# 01. 데이터 모델링의 이해 (이해는 Two Sun)
## 01.01 데이터 모델의 이해
### a. 데이터 모델링의 개념 및 특징
- 데이터 모델링의 개념 : 현실 세계를 단순화해서 저장하기
- 데이터 모델링의 특징 : 명단추 (이름난 단추라고 외울것)
    
    + 추상화 (Abstraction): 복잡한건 떼고 필요한 데이터와 관계만 남기고 저장 (복세편살 ST)
    + 단순화 (Simplification) : 복잡한 데이터를 이해하기 쉬운 구조로 표현하는 과정
    + 명확화 (Clarification) : 데이터의 구조와 관계를 명확하게 표현하여 오래의 여지를 없애는 과정
- 데이터 모델링이 올바르게 수행되지 않는 경우 (데이터 모델링의 중요성)
    |발생 문제|설명|
    |---|---|
    |중복성|같은 데이터가 여러 곳에 저장되어 관리가 비효율적이고 불일치가 발생할 수 있음|
    |비유연성|데이터 모델이 변화에 대응하지 못해 시스템 확장 혹은 수정이 어려움|
    |비일관성|동일한 데이터가 다르게 저장되거나 표현되어 데이터의 신뢰성이 저하됨|
### b. 데이터 모델링의 관점
+ 데이터 관점 (What) : **어떤** 데이터를 저장할 것인가! 를 중점으로 두는 관점
+ 프로세스 관점 (How) : 저장 된 데이터들을 어떻게 저장하고 어떻게 조회하고 어떻게 관리할 것인가. (데이터의 흐름등을 그림으로 표현)
+ 데이터와 프로세스의 상관 관점 (Interaction) : 데이터와 프로세스가 서로 상호 의존적이다 뭐 그런 이야기,,, (근데 아무래도 프로세스도, 데이터도 서로가 있어야 의미가 있으니까용)
### c. 데이터 모델링의 3단계
+ 데이터 모델링의 종류 : 개념점/논리적/물리적
    + 개념적 데이터 모델링 : 추상적으로 데이터를 개념적으로 설계한다. 
    + 논리적 데이터 모델링 : 논리적 단계와 속성을 설계한다.
    + 물리적 데이터 모델링 : 실제로 컴퓨터에 어떻게 저장할지 설계한다.
+ 세계
    + 개념 세계 : 개념 + 논리
    + 물리 세계 : 논리 + 물리
### d. 데이터 독립성 : 데이터 중복 제거를 통한 효율성 증진
+ 데이터 베이스 
    + 시스템 등장 배경 : 기존 파일 시스템으로 부터의 탈피
        + 파일 시스템 : 고객 주문 데이터/고객 관리 데이터 등을 따로 다른 파일로 관리하게 되면서 같은 정보가 중복되어 저장되는 문제 발생, 더 나아가 수정사항이 한쪽에만 반영될 경우 문제가 발생할 수 있음
    + 데이터 통합 관리 : 중복을 제거하고 하나의 데이터 베이스에서 관리
    + 데이터 공유 및 일관성 유지 : 같은 데이터 베이스에서 조회된 내용을 여러 프로그램에서 접근 및 관리
### e. 데이터 베이스의 3단계 구조
+ 외부 스키마 : 프로그램/사용자등이 볼 수 있는 모습. 검색/필터 적용 등과 같은... (소신발언! 케이스티 파이는 외부 스키마가 굉장히 별로다!)
+ 개념 스키마 : 중간에서 내부스키마에 저장 되어있는걸 조합해서 외부 스키마로 전환하기 위한 스키마
+ 내부 스키마 : 물리적으로 데이터를 저장하는 걸 말한다 (파일/인덱스 등등..)
### f. 데이터 종속성과 독립성
+ 데이터 종속성 : 데이터와 응용프로그램간의 상호의존 관계를 표현하는 단어. 종속성이 있다면 데이터 구조 수정 시 마다 응용프로그램에서의 수정이 필요하게 된다.
+ 데이터 독립성 : 종속성과는 반대되는 말로, 데이터 구조가 바뀌어도, 응용 프로그램은 수정이 필요 없는 것을 뜻한다. 아래의 두 독립성을 통해 전체적인 독립성을 유지하는 것이 좋다.
    - 논리적 독립성 : 개념 스키마가 변경 되어도 외부 스키마가 변경되지 않는 독립성
    - 물리적 독립성 : 내부 스키마와 개념 스키카의 독립성
+ 독립성이 유지 되지 않는 경우
    - 데이터 중복성과 데이터 복잡성 증가
    - 유지보수 비용 상승
### g. 데이터 모델링의 요소
+ 데이터 모델링의 3가지 구성요소
    |명칭|설명|
    |---|---|
    |엔티티|관리 해야할 객체(개체) (Thing이라고 생각하면 편함)|
    |속성|엔티티가 가지는 특성이나 정보/ 엔티티(학생) -> 성별, 나이와 같은 정보|
    |관계|엔티티간의 상호작용을 연결. 이를테면 나(객체)는 차(객체)를 소유한다.|
+ 스키마 VS 인스턴스
    - 이게 비교 대상이 되나? 스키마는 헤더고 인스턴스는 행 한개한개임

### h. 데이터 모델 표기법 및 ERD 작성 순서
+ peter-chen,IE,IDEF1X,ISO,UML,Barker's Notation (다양하게 있지만 두개만 알면된다고 하더라...)
+ IE표기법 
    - 최상단에 PK 
    - 0,|, <- 를 활용해서 어떤 관계인지 표현해야 합니다. 0:N,1:1,등등
+ Barker's 표기법
    - PK에 #붙이기
    - NOT NULL =>> * 붙이기
    - NULL 가능시 0 붙이기
    - 점선 실선으로 필수 여부 표시
+ ERD작성 순서
    - 엔티티 도출
    - 엔티티 배치
    - 엔티티 관계 설정
    - 관계명 설정
    - 관계 참여도 표현 (1:N 등)
    - 관계의 필수 여부 확인
+ 좋은 데이터 모델의 요건
    - 완전성 : 필요한 모든게 정의되어 있어야함
    - 업무규칙 : 모든 업무규칙을 담을 수 있게 정의되어야함 
    - 중복배제 : 동일한 사실은 한번만 기록해야함
    - 데이터 재사용 : 공통영역에 저장후 같이 사용해야함
    - 통합성 : 중복 배제 + 데이터 재사용

## 01.02 엔티티
### a. 엔티티의 개념
+ 엔티티의 정의 : 변별할 수 있는 여러 사물
+ 엔티티의 종류 : 
    - 유형 엔티티 : 물리적 형태가 있는 객체( 형태가 있는 객체!!)
    - 개념 엔티티 : 물리적인 형태는 없으나 관리해야할 정보(상의, 보험상품 등)
    - 사전 엔티티 : 발생하는 **사건**을 기록하는 엔티티 (수강신청!, 상품 주문!)
+ 엔티티와 인스턴스
    - 엔티티 : 약간 현실 정보 하나하나 들의 이데아
    - 인스턴스 :  개별 사물의 특징을 담은 정보
### b. 엔티티의 특징
+ 엔티티는 새당 업무에서 관리할 필요가 있는 정보를 포함해야 함
+ 유일한 식별자에 의해서 식별이 가능해야함 (PK)가 있어야함
+ 2개 이상의 인스턴스를 가지는 엔티티여야함
+ 업무에 의하여 CRUD가 발생해야함
+ 반드시 속성읠 가져야함 (엔티티만 있고 정보가 없으면 왜 만들었는데;;)
+ 주식별자만 존재하고 일반 속성이 없는 경우는 바람직하지 않음
+ 다른 엔티티와 최소 1개 이상의 관계를 가져야함
### c. 엔티티의 명명 원칙
+ 업무에 사용하는 용어 이용
+ 약어 사용 자제
+ 단수명사
+ 이름 중복 불가
## 01.03 관계
### a. 관계의 개요
+ 관계와 페어링 : 엔티티들을 서로 관계를 가지고 인스턴스끼리 연결되어있걸 페어링이라함
+ 관계의 분류 
    - 존재에 의한 관계 : 학생A는 경영학과 학생이다.
    - 행위에 의한 관계 : 학생이 수업을 수강한다/학생이 수강신청을 했다.
### b. 관계의 표기법
+ 관계명 : 양방향으로 이름을 설정해야 한다. (현재형으로 설정할 것) 
+ 관계 차수 : (1:N) (1:1) (N:M)
+ 관계 선택성 
    - 필수 참여 : 사원의 경우 소속 부서가 항상 필요하다
    - 선택 참여 : 부서의 경우 사원이 없어도 존재할 수 있다.
+ 관계 읽기 
    - 기준으로 읽으면 된다... 
    - 예시 : 각 사원은 하나의 부서에 반드시 소속된다.
    - 예시 : 각 부서는 여러명의 사원을 선택적으로 포함한다.
